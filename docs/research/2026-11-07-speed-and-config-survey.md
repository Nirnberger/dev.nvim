# inkmath.nvim: speed techniques, config conventions, interop (2026-11-07)

Method: shallow clones of snacks.nvim, image.nvim, render-markdown.nvim, markview.nvim, render-latex.nvim, mini.nvim, conform.nvim, which-key.nvim (main branch, read 2026-11-07), plus Neovim master `runtime/doc/{treesitter,api}.txt`, kitty `docs/graphics-protocol.rst`, vimtex `doc/vimtex.txt`. Paths below are repo-relative. Prior competitor survey (not repeated): `docs/research/2026-11-07-similar-plugins.md`. "(unverified)" = reasoning or recollection, not read in source.

## 1. Speed techniques actually used

| Technique | Who | Evidence |
|---|---|---|
| Visible-range-only detection | snacks | `lua/snacks/image/doc.lua` `find_visible` loops `win_findbuf`, `getwininfo` topline/botline, calls `find(buf, cb, {from,to})`, which passes `from-1,to` to `query:iter_matches` (doc.lua ~L225-262) |
| Same, with margin | render-markdown | `request/view.lua:9-20`: per-window range padded by 10 rows, ranges coalesced (`lib/interval.lua`); `View:parse` calls `parser:parse(range)` per range (L60-65) |
| Same + directional prefetch | render-latex | `lua/render_latex/viewport.lua:13-56`: `prefetch_lines=40`, shrinks to 1/4 for big buffers, skews prefetch toward scroll direction (top-prefetch/3 when scrolling down), `config.lua:63-66` debounce 75 |
| Partial rendering for big buffers | markview | `spec.lua:213` `max_buf_lines = 1000`; `lua/markview.lua:97` refuses full render above it; cursor-centred `edit_range`. Still calls `parse(true)` (`parser.lua:160,189`), so the full parse is not avoided |
| Async ranged parse | snacks | `lua/snacks/util/init.lua:460-469`: `parser:parse(range, on_parse)` when `has("nvim-0.11.4")`, else sync. Neovim doc (`treesitter.txt`, `LanguageTree:parse`): with a callback parsing is async, returns trees directly if it finishes within 3 ms, errors on 'redrawtime' timeout. Nobody else surveyed uses it |
| Debounce | snacks 100 ms (`inline.lua:15-22`) on `BufWritePost/WinScrolled/BufWinEnter` + `nvim_buf_attach on_lines`; placement update 10 ms (`placement.lua:106`); render-markdown 100 ms leading-edge (`lib/decorator.lua:96-110`: first call runs immediately via `vim.schedule`, calls inside the window are dropped); markview 25 ms for cursor (`autocmds.lua:384`), 150 for edits (`spec.lua:189`); render-latex 75 ms |
| Skip work when nothing changed | render-markdown | `core/ui.lua:76-111` `Updater:changed()` compares changedtick and "visible range already handled" (`Context.contains`); only re-parses when either differs, otherwise only re-applies hide/reveal (`display`) |
| Full clear and rebuild on change | render-markdown, snacks inline | `ui.lua:119,126-135` clears the whole namespace then re-sets all marks. Our incremental `on_bytes` path is already ahead of this |
| Extmark identity reuse | snacks | `inline.lua:update`: matches new finds to existing placements by `img.src`, creates only for new, deletes the rest; stats `{new,del,update}` |
| Transmit by path | snacks, image.nvim | snacks `image.lua:145-150`: `t="f", f=100, data=base64(path)` for local sessions; only when `terminal.env().remote` does it chunk base64 PNG (`t="d"`, L156-190). image.nvim `backends/kitty/init.lua:47-49,68-76`: `transmit_medium=file` locally, `direct` over SSH; an in-memory `transmitted_images[id] == preprocessing_hash` set avoids retransmission (L20,68-76,187) |
| Direct tty write | image.nvim | `backends/kitty/helpers.lua:9`: `vim.loop.new_tty(1,false)` stdout handle, tmux wrapping via `utils.tmux.escape` |
| Query/parse object reuse | all | `vim.treesitter.query.get(lang, name)` (cached by core) in snacks `doc.lua`; `get_parser(buf)` is cached per buffer. No plugin builds `Query` per update |
| Converter caching | render-markdown | `handler/latex.lua`: process-wide `Handler.cache[input]`, but conversion is **synchronous**: `vim.system(...):wait()` (L96-120). inkmath's async worker pool is already better |
| Terminal detection async | snacks | `terminal.lua:225-293`: XTVERSION query with 1 s timer, `vim.schedule`; under tmux it reads `client_termname` instead when extended-keys is on (L254-266, issue 2332); attach is deferred until detect finishes (`doc.lua:466-474`), attached from `FileType` via `vim.schedule` (`image/init.lua:280-292`) |

Not used by any surveyed plugin (grep over their `lua/` trees returned zero hits):
- `nvim_set_decoration_provider`. All of them keep persistent extmarks.
- `vim.uv.new_work` / threads. Tree-sitter objects cannot cross Lua states, so only the conversion step could move, and inkmath's node worker already does that.
- `register_cbs` / `on_changedtree`. Nobody uses the tree's changed ranges.
- Metadata caches for image dimensions. snacks and image.nvim shell out to ImageMagick for size.

Neovim facts relevant to inkmath (`runtime/doc/treesitter.txt`, `api.txt` master):
- `LanguageTree:register_cbs({on_bytes, on_changedtree(ranges, tree), ...}, recursive)`: `on_changedtree` gives exactly the syntactically changed ranges after each reparse.
- `LanguageTree:parse(range, on_parse)`: "Any region with empty range (typically only the root tree) is always parsed", so a range only limits injection children (markdown_inline, latex in markdown). The root tree is always incrementally reparsed in full.
- `nvim_set_decoration_provider`: `on_range` can return a skip position, `ephemeral` marks are redraw-only. "Not allowed to remove or update extmarks in on_line/on_range." Good for per-redraw hide/reveal, poor for conceal + virt_lines that must persist for layout.

Kitty protocol (`docs/graphics-protocol.rst`):
- Media `t=d|f|t|s` (L391-412). `t=t` deletes the file after read, only if in a temp dir and the path contains `tty-graphics-protocol`; `t=s` is POSIX shm. For PNG the terminal still decodes, so `t=s` only saves a file read, not a decode.
- Quota is 320 MB per buffer in kitty, oldest images evicted (L1193-1202). That is what makes the id LRU necessary. Ghostty's quota differs (unverified).
- Raw RGBA (`f=32`) skips the PNG decode but is ~10x larger on disk. With `t=f` that is only disk and page cache, not tty bytes. Likely not worth it at ~2 ms/render (unverified benefit).
- Images stay in the terminal across Neovim restarts until evicted or deleted. Re-attach can reuse ids if ids are stable per hash (e.g. derive id from the hash). Risky with several Neovims in one terminal (typst-concealer notes this clash, per prior survey).

## 2. What would cut our remaining costs

Context for the numbers: in markdown the treesitter highlighter parses the same trees during redraw, so a sync `parser:parse` in our `on_bytes` path moves cost, not removes it. In `.tex` under vimtex's recommended setup the highlighter is **off** (`doc/vimtex.txt:7400-7440` strongly advises against Tree-sitter highlighting for LaTeX), so the incremental reparse is entirely ours.

Ranked by expected payoff:

1. **Use `on_changedtree` ranges instead of the full re-detect fallback (38 ms).** `parser:register_cbs({on_changedtree=function(ranges, tree) ... end})` fires after any reparse (including the highlighter's), with the changed node ranges from `ts_tree_get_changed_ranges`. Query only those ranges (plus enclosing math nodes) with `iter_matches(root, buf, srow, erow)`. Replaces the "can't trust on_bytes, redo everything" path. The callback fires inside redraw, so hand work to `vim.schedule`. In markdown this removes our own parse trigger entirely: no sync `parse()` in the keystroke path, the highlighter's parse feeds us.
2. **Make the keystroke path parse-free and let it time-slice.** Where we must force a parse (tex without highlighter), use `parser:parse(range, cb)` (async, 3 ms slices, 0.11.4+ and 0.12) instead of sync, and only do the cheap shift/invalidate work synchronously. Debounce the detect, trailing, 30-50 ms in insert mode (peers use 25-100 ms), flush immediately on `InsertLeave`/`CursorHold`. Expected: the 14 ms tex and 30 ms md keystroke become "extmark shift only" (< 2 ms main-thread), with detection landing a frame later. Effect is perceived latency, not total CPU.
3. **Bound the query by viewport plus margin, not by buffer.** Full re-detect cost is query time over the whole tree. Apply snacks/render-markdown/render-latex's approach: query `[top-N, bot+N]` (render-markdown ±10 rows, render-latex 40 prefetch) and mark the rest "stale-unseen". Fill the remainder in idle slices (`vim.defer_fn`/timer, a few hundred rows each, cancel on edit) or lazily on `WinScrolled`. Cuts the 38 ms fallback roughly in proportion to visible/total lines (about 40/5000 rows), and this is also the biggest lever on attach.
4. **Cheap pre-filter before any tree work.** From `on_bytes`, read the changed line(s) with `nvim_buf_get_text` and test for `$`, `\(`, `\[`, `\begin`, `\end`, ```` ``` ````, `\\` plus "edit is inside a known span" (extmark lookup). If neither, only shift. Nothing surveyed does this (suggestion, not precedent), but it makes the common keystroke (prose) skip detection entirely.
5. **Attach 20-35 ms.** (a) Do it like snacks: attach from `FileType` through `vim.schedule`, never inside the event. (b) Spawn workers lazily on the first cache miss, not in `setup`/attach; most reopened buffers are 100% cache hits. (c) Visible-range-first detection (item 3), then idle fill. (d) Read PNG size from the file header (IHDR: width/height are big-endian u32 at bytes 16-23, `uv.fs_open/fs_read` 24 bytes) or encode `WxH` into the cache filename, so no ImageMagick call and no separate metadata file. Neither snacks nor image.nvim does this. (e) Check cache hits with a batch of `uv.fs_stat` callbacks instead of blocking `filereadable`. (f) Keep `vim.fn.*` out of per-node loops (snacks calls `getwininfo`/`win_findbuf` once per update, which is fine).
6. **Do not bother with:** decoration-provider placement (persistent extmarks are required for conceal + virt_lines layout, and no peer does it), `uv.new_work`, shared memory transmission, raw RGBA.

## 3. Configuration conventions (what to copy)

- **Entry points.** render-markdown `plugin/render-markdown.lua`: `vim.g.loaded_render_markdown` guard, then `require('render-markdown').setup(vim.g.render_markdown_config)` plus colors/command/log/manager init. So it works with no `setup()` call and accepts `vim.g` config; lazy.nvim `opts = {}` also works. Auto-detects lazy.nvim `ft` for `file_types` (`init.lua:161-166`). which-key and conform ship a tiny `plugin/*.lua` that only registers commands (`plugin/conform.lua:1` `ConformInfo`; `which-key/config.lua:306` `:WhichKey`). mini.nvim requires `setup()` and keeps `MiniX.config` plus `vim.b.minix_config` merged per buffer (`mini/cursorword.lua:27,177-178`).
- **Disable switches.** mini: `vim.g.minicursorword_disable` / `vim.b.minicursorword_disable` (`cursorword.lua:47,175`). snacks: `vim.g.snacks_<module>` / `vim.b.snacks_<module>` (indent, scroll, animate, words, dim, scope; and `vim.b.snacks_image_conceal` as a per-buffer override read in `image/inline.lua`). conform recipe: `vim.g.disable_autoformat` / `vim.b[bufnr].disable_autoformat` checked in a `format_on_save` function, toggled by a `:FormatDisable[!]` command where `!` means buffer-local (`doc/recipes.md:50-105`). Recommended for inkmath: `vim.g.inkmath_disable`, `vim.b.inkmath_disable`, `vim.b.inkmath_config`.
- **`enabled` as boolean or function, per-ft/buf overrides.** render-markdown: `enabled`, `ignore = function(buf)`, `max_file_size = 10.0` (MB), `overrides = { buftype, filetype, buflisted, preview }` (`settings.lua:1476-1479`), `win_options` with rendered/default states, `render_modes`. snacks accepts functions for values (`doc.conceal = function(lang, type)`, used in `inline.lua`). markview: `preview.filetypes`, `modes`, `hybrid_modes`, `max_buf_lines`.
- **Commands.** One command with subcommands and completion, rather than many: `:RenderMarkdown <method> [bool]` completes from the public API table keys (`core/command.lua:14-49`), reports errors through `vim.notify`. Same shape recommended: `:Inkmath enable|disable|toggle|clear|refresh|info|health`, plus bang-less buffer-local variants.
- **`<Plug>` mappings and keymaps.** No default keymaps; expose `<Plug>(inkmath-toggle)` etc. and document a sample mapping. vimtex's convention is `<plug>(vimtex-a$)` (`vimtex.txt` text-object refs, ~L5203). Default keymaps, if any, behind `keymaps = false` opt-in. Always set `desc`.
- **Highlights.** `nvim_set_hl(0, name, {default = true, ...})` and links so colorschemes win (`mini/cursorword.lua:171-172`, `render-markdown/core/colors.lua:80,85`). For inkmath: derive image fg/bg from `Normal`/`Conceal` and re-render on `ColorScheme` (typst-concealer and latex-preview do this per prior survey).
- **Events.** markview fires `User` events with `data`: `MarkviewAttach/Enable/Disable/Detach/HybridEnable/HybridDisable/SplitviewOpen/Close` (`markview/actions.lua:354-373`), and also calls a `preview.callbacks` table. mini fires `User Mini*` via `H.trigger_event` (`mini/files.lua:3113`), snacks `SnacksDashboard*`, `SnacksProfilerStarted`. render-markdown has **no** User events (zero `nvim_exec_autocmds` in `lua/`); it uses `on = { attach, initial, render, clear }` callbacks. Recommend both: `User InkmathAttach|Detach|Enable|Disable|Rendered` with `data = {buf, win?}` and an `on_*` callback table.
- **Public API.** render-markdown `api.lua`: `enable/disable/toggle/buf_enable/buf_disable/get/set/render({buf, win, config})`. Mirror: `require('inkmath').enable(buf)`, `.is_enabled(buf)`, `.refresh(buf)`, `.get_spans(buf)` (so other plugins can ask "what ranges are you rendering").
- **Health and docs.** `lua/<name>/health.lua` (render-markdown, markview, snacks `Snacks.health`) checking Neovim version, parsers present, terminal graphics support, tmux `allow-passthrough`, node and tectonic. `doc/<name>.txt` vimdoc with tags; render-markdown also ships `doc/limitations.md`, `troubleshooting.md`.
- **Lazy-loading friendliness.** `plugin/` file does nothing but guard + `nvim_create_user_command` with a lazy `require` inside the callback; attach on `FileType` (+`vim.schedule`) for only the supported filetypes; no `setup` required. snacks attaches the image doc module from a `FileType` autocmd filtered by treesitter lang (`image/init.lua:280-292`).

## 4. Interop

- **render-markdown.nvim.** Has its own `latex` handler (`handler/latex.lua`, registered at `core/handlers.lua:12`): for each `latex` node in markdown_inline it runs `utftex`/`latex2text` and writes Unicode virt_lines above/below (`settings.lua:1203-1226`; defaults `enabled = true`, `converter = {'utftex','latex2text'}`). If neither binary is installed it silently does nothing (`ConverterNotFound`, handler L36-40). No hook to exclude ranges. Ways to coexist: (a) user sets `latex = { enabled = false }`; (b) `custom_handlers = { latex = { extends = false, parse = function() return {} end } }` (`doc/custom-handlers.md`) to replace it; inkmath cannot do either safely on its own, so detect `package.loaded['render-markdown']` in health and warn, and document the snippet. Namespaces are separate (`M.ns` in `core/ui.lua`) and it clears only its own. Other overlap: it sets window options per render state, `conceallevel` rendered = 3 (`win_options`, `settings.lua:1866`), default state = your `vim.o.conceallevel`. Our conceal extmarks depend on `conceallevel >= 2`, so health should check it, and we must not set it ourselves. It un-conceals the cursor row (anti_conceal); inkmath's reveal should key off the same row so the two do not fight. It exposes `on.render`/`on.clear` callbacks we can listen to for re-asserting after its full clear/rebuild.
- **markview.nvim.** Own latex renderer (`renderers/latex.lua`, config `lua/markview/config/latex.lua`, `enable = true` at L66), Unicode-symbol based. Disable with `latex = { enable = false }` (path from the config files; not exercised). Fires `User Markview*` events (above), so inkmath can re-sync after `MarkviewEnable/Disable/HybridEnable`. Switches to partial rendering at 1000 lines (`spec.lua:213`) and sets `conceallevel=3`, `concealcursor` by mode (`spec.lua:68-110`), so same conceallevel caveat. `spec.lua:223` `renderers = {}` lets users add custom renderers.
- **snacks.image.** Also renders math from treesitter for markdown and latex (`image/init.lua:138` `math.enabled = true`, `:74` `doc.enabled = true`). Running both double-renders. Disable with `image = { doc = { enabled = false } }` or `math = { enabled = false }`. Health: warn when `package.loaded['snacks.image']` and `Snacks.image.config.doc.enabled/math.enabled`. It also sets `allow-passthrough all` on tmux itself (`terminal.lua:243`). Image-id spaces are separate counters; use a high randomized id base to avoid collisions (kitty ids are global per terminal window).
- **image.nvim (and molten/quarto output).** `backends/kitty/init.lua:193-204` clears with `display_delete = "a"` (kitty `d=a`: all placements visible on screen). Virtual (`U=1`) placements are placements too, so that command would likely blank our images until re-placed (unverified; test it). Mitigate: re-send `a=p,U=1` on `FocusGained`/`WinScrolled`/`User` redraw if a placement vanished, and keep image data transmitted (a=t) so re-placement is cheap. molten-nvim renders cell output through image.nvim or snacks into its own virt_lines, not our namespace; quarto-nvim needs the `markdown` parser registered for `quarto` (`vim.treesitter.language.register('markdown','quarto')`, from recollection, unverified) so our `FileType` list should include `quarto`, `rmd`.
- **vimtex.** Recommends Tree-sitter highlighting off for tex but the `latex` parser still available "to plugins that query the syntax tree" (`vimtex.txt:7400-7440`), exactly our case; this is also the situation where the parse cost is ours (section 2). Its conceal is syntax-based (`g:vimtex_syntax_conceal`, `:2647`; `g:vimtex_syntax_conceal_disable`, `:2733`) and its math text objects depend on its syntax groups, which we do not touch. Open question to test: syntax conceal (`\alpha`, super/subscripts) inside spans where we also place a `conceal` extmark. Needs a quick manual test of which wins; if there is a visible clash, document `vimtex_syntax_conceal_disable` or conceal whole spans with `end_col` extmarks.
- **nvim-cmp / blink.cmp.** Placeholder images are ordinary cells (U+10EEEE plus diacritics), so floating windows overwrite them like text. This is the structural advantage over image.nvim, which must hide images under floats. Remaining issue: display math uses virt_lines/overlay; completion menus anchored below a line with tall virt_lines may position by screen row, fine. Low risk. Flicker risk during insert-mode re-renders if the popup is open (debounce, item 2).
- **noice.nvim.** Moves cmdline/messages to floats, no extmark interaction with buffer text; low risk (unverified). Messages area is outside buffer windows so placeholder cells are unaffected.
- **nvim-ufo / folds.** Fold providers only change fold ranges and fold text (`nvim-ufo` README: provider_selector, foldtext virt_text). Neovim does not draw virt_lines of lines inside a closed fold (unverified), so no leak; but `conceal_lines` on a folded range plus a fold boundary is the likeliest edge (snacks hit related cropping issues: snacks issues 2391, 2569 from prior survey). Test: fold start line inside a display math overlay.
- **obsidian.nvim.** The render-markdown ecosystem doc lists obsidian.nvim's UI as clashing with concealing renderers (`render-markdown/doc/markdown-ecosystem.md:12-14`); obsidian users run `ui = { enable = false }` with render-markdown/markview. It does no math rendering, so no direct conflict with inkmath; whether newer forks changed their UI default is unverified.
- **Neutral baseline for the "other renderer present" case.** One ownership rule is enough: inkmath owns math spans only (its own namespace, its own conceal), the markdown renderers own everything else, and health tells the user which math handler to switch off. No surveyed plugin lets an external plugin claim ranges, so inkmath can offer the first such hook: `require('inkmath').get_spans(buf)` and `User InkmathRendered` for other renderers to avoid those rows.
